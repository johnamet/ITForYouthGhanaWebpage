# Descriptor-Driven CMS Rollout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extract the Laptop Bank's descriptor-driven admin CMS into a shared kit, then apply it wherever it fixes a real defect — starting with the 22 admin write routes that currently record no audit entry.

**Architecture:** One `ContentTypeDescriptor` per editable thing; one renderer, one CRUD layer, one gated-and-audited API route pair, one registry entry. Page copy gets its fields generated by walking its own seed content, so a string added in code becomes editable with no second edit. Bespoke forms survive only where the UI genuinely needs to be bespoke.

**Tech Stack:** Next.js 14 App Router, React 18, TypeScript 5.7, Tailwind 3.4, zod 3.24, firebase-admin 13. No new dependencies.

**Reference implementation:** `lib/content/laptop-bank-admin-schema.ts`, `lib/cms/laptop-bank-admin.ts`, `components/admin/laptop-bank-record-form.tsx`, `app/(admin)/admin/laptop-bank/records/[type]/`, `app/api/admin/laptop-bank/records/[type]/`
**Prior ledgers:** `docs/superpowers/2026-09-01-laptop-bank-execution-ledger.md`, `docs/superpowers/2026-09-02-laptop-bank-admin-execution-ledger.md`

## The case, in numbers

Measured on this branch, not estimated:

| | Count |
|---|---|
| Bespoke admin form components | 28 |
| Lines across them | **9,078** |
| Lines in the entire Laptop Bank descriptor system | **1,155** |
| Editors that system provides | 21, including 202 generated page-copy fields |
| Admin API routes | 45 |
| Admin API routes that write **without** an audit entry | **22** |
| Admin API routes not session-gated | 1 (`session/route.ts` — correct, it *is* the login) |
| Forms showing any bespoke-UI need (rich text, upload, reorder) | 3 of 9 sampled |

**But LOC is not the argument, and this plan does not chase it.** Migrating a
working form carries regression risk on a live CMS and pays nothing back on its
own. The argument is what the descriptor pattern gives for free that 22 of these
routes do not currently have: an audit entry naming the actor, range validation,
guidance text carrying the *why*, and registration somewhere the sidebar
actually reads.

So the sequencing is: **fix the defects first, extract the kit second, and
migrate only where migration removes a real gap.** Tier D below stays bespoke
on purpose.

## Global Constraints

Every task's requirements implicitly include this section.

**Never migrate a working form for tidiness alone.** Each migration task must
name the specific gap it closes (no audit entry, no validation, no override
path, no discoverability). If a form has none of those gaps, leave it.

**Every admin write path is gated and audited.** `requireAdminApiSession()`
first, validation second, `{ configured: false }` → 503, then `writeAuditLog`
with the actor from `getCurrentAdminUser()`. A route that writes without an
audit entry is the defect this plan exists to fix — do not create new ones.

**Auth is checked before existence.** An unknown type returns 401 to an
anonymous caller, never a 404 that reveals which types exist.

**Empty means "not overridden", never "blank this out".** A heading cleared by
accident must fall back to its seed. Removing a section is a structural change
and stays a developer job. This is the rule that makes CMS overrides safe to
hand to a non-developer, and it is already implemented in
`lib/cms/laptop-bank-pages.ts` — reuse it, do not reinvent it.

**Readers strip non-plain values.** Every CMS reader passes stored data through
`toPlainData` from `lib/utils/plain.ts`. A Firestore `Timestamp` reaching a
Client Component logs an error on every prerender and still exits 0, which is
how it went unnoticed on `/partner-with-us` for weeks.

**A publishing decision gets a publishing interface.** Any field that decides
whether something appears publicly — a consent flag, a `status: published`, a
`permission on file` checkbox — renders in the amber panel with an explicit
sentence about what turning it on does, and never defaults to the publishing
value. See `ConsentWrapper` in the reference implementation.

**Counts cannot be negative.** Number fields declare `min`/`max`. A real record
reached Firestore with `units_offered = -70` before this existed.

**No test runner in this repo.** Verification per task is:

```bash
npm run type-check && npm run lint && npm run build
```

plus live route checks against `npm run start`, plus `npm run verify:cms` once
Task 2 exists. A task is not done until those have run and their output has been
read.

**Killing a dev server:** `pkill -f "next dev"` matches the parent, not the
`next-server` child it spawns. Use `pkill -f next-server`, and check
`ss -ltn | grep 3000` before trusting a `curl` result — two verification rounds
in this programme were silently answered by a stale server.

## Migration tiers

**Tier A — defects (Tasks 2, 3).** The 22 unaudited write routes, and any
content area with no override path at all.

**Tier B — flat record collections (Task 4).** Clean field lists, low risk,
and they gain audit + validation + guidance. Measured shapes:
`TeamMemberProfile` 13 flat fields, `JobListing` 10 flat, `Partner` and
`Testimonial` both small and flat.

**Tier C — nested page content (Task 5).** Needs the seed-walk generator, not a
hand-written field list. `DepartmentProfile` has 24 fields with 8 nested or
array members; `impact-page-form.tsx` is 655 lines; `what-we-do-forms.tsx` 670;
`site-page-form.tsx` 893 and already reused across five routes, so it is
closest to the pattern already.

**Tier D — stays bespoke, deliberately.**
- `article-form.tsx` (719) — editorial writing surface. A generated field list
  is worse than a purpose-built one for long-form authoring.
- `user-form.tsx` (264) — roles and permissions. Security-sensitive, and a
  generic renderer would make a privilege field look like any other field.
- `settings-form.tsx` (134) — deployment configuration, not content.
- `admin-login-form.tsx` (150) — authentication.
- `components/admin/json-editor.tsx` — **currently imported by nothing.** Delete
  it in Task 1 rather than carrying dead code that invites raw-JSON editing.

/**

```ts
// lib/cms/descriptors/audit.ts
import { getCurrentAdminUser } from "@/lib/cms/admin-auth";
import { writeAuditLog } from "@/lib/cms/audit";

/**
 * Runs a CMS write and records who did it.
 *
 * Exists because 22 of this repo's 45 admin write routes recorded nothing,
 * which made /admin/audit quietly incomplete: a change made through one of
 * them could not be attributed to anyone. Routing every write through one
 * wrapper means a new route gets the audit entry by construction rather than
 * by the author remembering.
 *
 * The audit entry is written AFTER the write succeeds and never fails the
 * request: losing the trail for one change is bad, but refusing a legitimate
 * content save because the log was unavailable is worse.
 */
export async function auditedWrite<T extends { configured: boolean }>(options: {
  action: "create" | "update" | "delete";
  resourceType: string;
  resourceId: string;
  summary?: string;
  changes?: Record<string, unknown>;
  write: () => Promise<T>;
}): Promise<T> {
  const result = await options.write();
  if (!result.configured) return result;

  const actor = await getCurrentAdminUser();
  await writeAuditLog({
    action: options.action,
    resourceType: options.resourceType,
    resourceId: options.resourceId,
    actor: actor ? { uid: actor.uid, email: actor.email, role: actor.role } : null,
    summary: options.summary ?? null,
    changes: options.changes ?? null,
  }).catch((error) => {
    console.error("Audit write failed", error);
    return { configured: false, written: false } as const;
  });

  return result;
}
```

## Self-Review

**Coverage against the stated goal.** Extraction → Task 1. The 22-route audit
gap → Task 2. Generic routes → Task 3. Tier B → Task 4. Tier C → Task 5.
Verification → Task 6. Tier D is explicitly out of scope with reasons given.

**Risks, named:**

- **Deleting a working form is irreversible from a user's point of view** if
  the descriptor misses a field. Every migration task therefore verifies the
  generated field count and the public route *before* the delete step, and the
  delete happens in the same commit so a revert restores both halves together.
- **`site-page-form.tsx` is reused by five routes** including
  `/admin/content/who-we-are`. It is the highest-risk migration in Tier C and is
  deliberately left until last in Task 5, after the pattern has been proven on
  five smaller areas.
- **Live data exists.** `laptopBankMetrics/current` already holds a real record.
  Any verifier that writes must guard against real ids and clean up in a
  `finally`, as `verify:laptop-bank` does — and must skip an assertion rather
  than refuse to run, which is the mistake that earlier disabled the mandated
  consent checks.

**The one decision that changes this plan.** Tasks 1–3 are unambiguously worth
doing: they close a real defect (22 unaudited routes) and cost no form
migrations. Tasks 4–5 delete ~3,900 lines of working forms to gain audit,
validation, guidance and generated fields. If the preference is to keep working
forms alone, stop after Task 3 and the audit gap is still closed — but the
inconsistency stays, and each future area keeps costing a bespoke form.

**Type consistency.** `getDescriptor(key)` is the single lookup used by the
generic routes, the registry generation and `verify:cms`. `ContentTypeDescriptor`
gains exactly one field in this plan (`hub: string`, Task 3 Step 3).
`applyOverrides(seed, stored)` and `buildSeedFields(seed)` keep those signatures
in Tasks 1, 4 and 5. `auditedWrite` takes `write: () => Promise<T>` where
`T extends { configured: boolean }`, matching every existing CMS writer's return
shape in this repo.
